Setup Guide

A screenshot walkthrough of the four things you'll do most, using sample data end to end so every screen below matches what you'd actually see.

Create an Integration

An Integration represents one third-party system that will send data into the queue — an ERP, a POS, a logistics platform, anything that needs to call into your backend without calling it directly. Each one gets its own AES-256 key and IV, so a problem with one third party's credentials never affects another's. Create the integration first; a Transmission Channel always belongs to one.

1

Open Integrations and click "+ New integration"

The Integrations list shows every third-party system you've onboarded, its description, and its authentication key/IV (masked, with a one-click Copy button — the backend still returns the real values to any signed-in console admin, this is just a display choice so they aren't sitting in plain text on screen). Below, four are already set up: Saffron ERP, Suvidha POS, Bharat Logistics Hub, and Anand Retail Systems — a small ERP, point-of-sale, logistics, and loyalty stack, which is what the rest of this guide is built around.

Use the search box to narrow the list by name or description as it grows — searching "sync" here, for instance, would show only these four.

2

Fill in the name and generate a key + IV

Give the integration a name and a short description — the description shows up right in the list, so make it say what the system actually does, not just what it's called. Then set:

Authentication key — exactly 32 characters, used as the AES-256 key. Authentication IV — exactly 16 characters, the initialization vector. Both travel to the third party out of band (Slack, a shared doc, however you hand off credentials today) — Queue Manager never transmits them anywhere itself, it only stores them to decrypt what comes back in.

Save the key and IV somewhere safe the moment you generate them — you'll hand them to whoever implements the sending side, and they're exactly what the downloadable sample integration doc (see the next topic) fills in automatically, so you rarely need to copy them by hand more than once.

3

Save

The integration now appears in the list, sorted alongside the rest, and is ready to be attached to one or more Transmission Channels. Nothing is listening for traffic yet — an integration on its own doesn't expose any URL — that only happens once you build a channel on top of it, which is the next topic.

Set up a Transmission Channel

A Transmission Channel is one entry point URL that the third party posts encrypted payloads to. Behind it, Queue Manager fans requests out to one or more destinations at a controlled, throttled pace — so a burst from the third party never turns into a burst against your real backend. The "New transmission channel" dialog walks through this in three steps; the two channels used for screenshots below cover both shapes a channel can take.

1

Open Transmission Channels and click "+ New transmission channel"

Each row shows which integration the channel belongs to, its entry point, how many destinations it fans out to, its retention (TTL), and whether it's active. Below, Order Sync (Saffron ERP) is a simple one-destination channel; Bill Settlement Sync (Suvidha POS) fans out to two destinations by payment method; Shipment Status Sync is active; and Loyalty Points Sync is currently inactive — a normal state for a channel that's paused, being reconfigured, or not live yet.

2

Step 1 — Channel Detail

Pick which Integration this channel belongs to, then give the channel its own name and description, separate from the integration's. One integration can own several channels — Suvidha POS, for example, might eventually have a channel each for bill settlements, refunds, and shift closures, all sharing the same authentication key/IV but each with its own entry point, retention, and destinations.

3

Step 2 — Channel Setup

Set the Entry point slug — this becomes the path third parties POST encrypted payloads to (use "Copy URL" to grab the full ingest URL to hand off), and Keep transmission requests for (days) — how long a request's record stays queryable before it's cleaned up automatically.

Then add one or more Destinations, each with its own endpoint URL and Gap between sends (seconds of pacing between consecutive deliveries to that destination — this is the throttle that protects the real backend). With a single destination, like Order Sync's Inventory API, every request that arrives goes straight there — no routing configuration needed at all.

Add a second destination and a Routing field box appears above the destinations list. Bill Settlement Sync below names that field payment_type, and its two destinations — UPI Payments API (routing value upi) and Card Payments API (routing value card) — each claim one value. When a payload arrives, Queue Manager reads payment_type out of the decrypted JSON and hands the request to whichever destination's value matches — a single lookup at the moment it arrives, so it stays fast and simple even with several destinations.

4

Step 3 — Review

Review shows every destination with its resolved routing rule in plain language — "UPI Payments API — routes when payment_type = upi" — so you can sanity-check the whole fan-out at a glance before committing. From here, "Download sample integration doc" generates a Markdown file with the real ingest URL, the required headers, the AES-256-CBC encryption recipe (the exact PHP snippet a third-party developer would use), the integration's key/IV already filled in, the routing key and its values if this channel routes, and — per destination — a sample plaintext JSON body, that same body already encrypted with the integration's real key/IV, and a ready-to-run curl command built from it. The encrypted samples are generated live in your browser, so the curl commands in the file are genuine working requests, not placeholders — copy one straight into a terminal to smoke-test the channel before any third party writes a line of code. Hand the file to whoever's implementing the sending side and there's nothing left for them to guess.

5

Save, then activate

Saving creates the channel in an inactive state — nothing is listening yet. Click "Activate" on its row to start a worker processing for each destination; the entry point only starts accepting traffic once this happens. "Deactivate" reverses it without deleting anything — requests already waiting for a destination stay queued untouched, so pausing a channel to fix a downstream issue never drops a backlog. Loyalty Points Sync below is a real example of a paused channel sitting in exactly that state.

Monitor & retry Transmission Requests

Every payload that hits a channel's entry point becomes one Transmission Request — this is the single place to see everything that has flowed through the queue, in every state, across every channel and destination, and to step in by hand when something on the receiving end goes wrong.

1

Open Transmission Requests

Narrow the grid with the dropdowns — by transmission channel, by status (pending, processing, success, failed), or by a date range — then click Filter, or search the currently loaded rows by request ID or channel name. The coloured rail on the left edge of each row is the fastest way to scan a long list for trouble: green for success, red for failed, at a glance without reading the Status column at all.

Below, ten requests have already landed across all four channels — order events from Saffron ERP, UPI and card settlements from Suvidha POS split correctly by the routing rule you set up above, shipment updates from Bharat Logistics Hub, and loyalty accrual events from Anand Retail Systems, all successful, plus one Order Sync request that failed and was retried.

2

Open a failed request

Click "View" on any row to see its full detail: which channel and destination it was headed to, the exact destination endpoint URL that was called, the request's decrypted body exactly as it was received (handy for confirming the third party is actually sending what you expect), and the raw response — HTTP status plus body — that came back from the destination. Below, a Saffron ERP order for customer Anil Deshmukh failed with an HTTP 500 because the Inventory API was temporarily pointed at a broken endpoint; the response body makes the reason obvious without needing to check server logs.

3

Retry it

Fix the underlying problem first — in this example, that means correcting the destination's endpoint URL back on the Transmission Channel — then click Retry from the detail dialog or straight from the grid row. Queue Manager always re-publishes against the destination's current configuration, not whatever was in effect at the moment it first failed, so "fix the endpoint, then retry" genuinely works. The retry count on the row ticks up by one and the original decrypted payload is reused as-is — nothing is re-entered, re-typed, or re-encrypted by hand. Below, the same request now shows Success, HTTP 200, and one retry.

Retry is always a manual, deliberate action — Queue Manager never auto-retries a failed request on its own. That's a conscious choice: a downstream outage shouldn't turn into a retry storm hammering the same broken endpoint.

Manage your team

Console Admins are the people who can sign in and manage this console. They're added here by an existing admin, not through public sign-up — there's deliberately no registration page.

1

Open Console Admins

The very first admin ever seeded on a fresh install becomes the Super Admin automatically — that's Rohan Mehta below. Only a Super Admin can create new console admins or turn off someone else's two-factor authentication; every other admin can see this list, including everyone's role and 2FA status, but can't edit it, add to it, or act on anyone but themselves. Ananya Iyer already has 2FA on, Vikram Nair is mid-enrollment ("Pending setup" — created with 2FA required, hasn't finished scanning the QR code yet), and Rohan Mehta hasn't turned it on for his own account yet.

2

Create a new console admin

As a Super Admin, click "+ New console admin" and fill in their name, an optional contact number, email, and a starting password (at least 8 characters — they can't change it themselves yet, so pick something you'll hand off securely). Check "Require two-factor authentication setup before first login" — shown checked below for Vikram Nair — to force them through QR-code enrollment with an authenticator app the very first time they sign in; they can't reach any other page in the console until they've confirmed a valid code. Leave it unchecked and they can sign in with just their password and opt into 2FA later on their own terms.

3

2FA after that: self-service on, Super Admin off

Turning 2FA on is unrestricted self-service for every admin, regardless of role — from this same list, at any time, you can enable it for your own account, no one else's approval needed, because scanning your own QR code can't affect anyone but you.

Turning it back off is deliberately one-directional: only a Super Admin can disable another admin's 2FA, and not even for their own account without going through the same super-admin path. That asymmetry is intentional — disabling an already-active protection is treated as a recovery action that needs a second party involved, exactly the situation you're in when someone loses their phone or reinstalls their authenticator app and needs back in.
